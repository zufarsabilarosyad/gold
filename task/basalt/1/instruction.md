Step definitions in Basalt support retry configurations (`RetryPolicySpec`) and failure actions (`OnFailureAction`), but `WorkflowRunner` currently treats any step failure in an execution level as an immediate workflow abort.

Implement retry execution and failure policy handling in `WorkflowRunner`. When a step fails and has `on_failure` set to `OnFailureAction.RETRY`, re-execute the step callable up to `max_retries` additional attempts (total attempts = `1 + max_retries`) until it succeeds, exhausts its retry budget, or execution is cancelled. Calculate backoff delay intervals from the step's `retry_policy`; when `jitter` is `False`, the calculated delays must be strictly deterministic. Dispatch `LifecycleEvent.STEP_START` on each attempt, `LifecycleEvent.STEP_RETRY` before sleeping between attempts (carrying `attempt`, `delay_seconds`, and `error`), and `LifecycleEvent.STEP_SUCCESS` or `LifecycleEvent.STEP_FAILURE` on completion. When a step recovers after retrying, downstream dependent steps must execute normally.

Preserve `OnFailureAction.FAIL_FAST` as the default failure behavior: a terminal step failure skips all remaining pending steps across subsequent execution levels. When a step specifies `OnFailureAction.CONTINUE`, terminal failure skips its direct and transitive dependants, but independent branches and later steps without dependencies on the failed step must continue executing to completion. If any step ends in failure, `StateMachine.aggregate_workflow_state` must report overall workflow state as `WorkflowState.FAILED`.

When a run is cancelled via `WorkflowRunner.cancel_run` during step execution or during a retry backoff wait, abort execution immediately, prevent any subsequent retry attempts, and mark the step and workflow state as `CANCELLED`. Persist step execution attempt counts in `StepRunModel.attempt` via `BasaltRepository.save_run_result`, and include attempt counts in run status API responses and CLI output formatting.
