Basalt's workflow runner currently treats any step failure as an instant abort for the entire run, skipping remaining work and ignoring retry configurations or failure continuation actions. We want `WorkflowRunner` to actually execute retries and handle non-blocking failure branches properly.

Track per-step attempt counts by adding `step_attempts: dict[str, int] = Field(default_factory=dict)` to `WorkflowRunResult`. When a step fails with `on_failure: retry`, retry it up to `max_retries` additional times (so total attempts equal 1 plus `max_retries`) using its policy backoff delay. When `jitter` is disabled, delay calculation must be deterministic. Emit lifecycle events for each attempt: fire `STEP_START` with the current attempt, `STEP_RETRY` before sleeping between attempts (carrying `attempt`, `delay_seconds`, and `error`), and `STEP_SUCCESS` or `STEP_FAILURE` on completion (including `attempt` and `error`). If a retried step recovers, let downstream dependent tasks execute as normal.

Preserve `fail_fast` as the default failure behavior, which aborts all downstream work across later levels on terminal failure. When a step uses `on_failure: continue`, skip its direct and transitive children, but allow independent parallel branches and unrelated later steps to finish running. If any step fails terminally under `continue`, mark the overall workflow status as `FAILED`.

Cancelling an active run while a step is executing or waiting in retry backoff must halt execution immediately, prevent any future attempts, and leave the workflow in a `CANCELLED` state. Persist attempt counts in SQLite storage (`StepRunModel.attempt`), and expose them through run status REST API responses and CLI output formatting (`Attempts` column in status tables and `attempt` in step details).
